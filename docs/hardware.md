# Hardware evidence and programming limits

## Observed unit and current F-key map

The user identified an upright keypad with a single knob above two columns of three keys. The connected USB unit had VID `0x1189`, PID `0x8890`, one configuration, and four interfaces. The configuration interface was interface 1: HID class/subclass/protocol `3/0/0`, one interrupt OUT endpoint `0x02` with a 64-byte max packet, and a 36-byte vendor-page HID descriptor. The descriptor defines Report ID 3 with 64 data bytes in each input and output report. Location ID is connection evidence, not a durable device identity; discovery does not pin a dock or port.

The original target-only capture mapped the six keys and three knob gestures to distinct keyboard usages. Earlier approved letter assignments produced `bfaexd` for the keys and `j`, `g`, `h` for clockwise, counterclockwise, and press. A later approved slot-1 write changed its recorded restore target from `x` to `z`; the user observed bottom-left typing `z` after one reconnect. The separately approved F16–F24 remap then changed layer-1 slots 1–6 and 13–15. After the Stage 1 reconnect check and Stage 2 writes, the user reconnected again; a target-only capture observed the following current map, with each usage producing a down/up pair:

| Upright physical control | Layer-1 slot | Current function key | USB keyboard usage | Recorded restore target |
| --- | ---: | --- | ---: | --- |
| Top-left key | 3 | F18 | `0x6D` | `b` (`0x05`) |
| Top-right key | 6 | F21 | `0x70` | `f` (`0x09`) |
| Middle-left key | 2 | F17 | `0x6C` | `a` (`0x04`) |
| Middle-right key | 5 | F20 | `0x6F` | `e` (`0x08`) |

## Software boundary

`KeyboardHIDInputEventProducer` is a read-only host capture adapter for the observed F16–F24 map. Before capture it requires already-granted Input Monitoring access, looks only for the USB `0x1189:0x8890` keyboard application collection, requires one current matching collection, and compares its transient IORegistry identity across two target selections. It also requires exactly one keyboard application-collection pair and a complete, unambiguous input layout for the nine observed usages. It never calls the permission-request API and opens with the non-seizing HID option. Discovery has no input callback; the live callback matches only validated keyboard-page element cookies from the selected collection. The registry entry binds the pre-open checks to one current attachment; it is not a durable serial identity and cannot distinguish a same-ID replacement that is already the sole matching unit.

The descriptor validator supports individual keyboard usage elements and fails closed when a target-overlapping usage array appears. Value callbacks do not expose the full HID report boundary needed to prove complete slot coverage or whether a held usage moved between slots before or after its old slot generated a release; guessing would risk a false release/repress or a duplicate F23 press. Missing usages, ambiguous devices, array layouts, or a changed target therefore refuse capture. The decoder emits key down/up for F16–F21, counterclockwise `-1` and clockwise `+1` rotations for F22/F24, and one dial-press callback on F23 down. Duplicate transitions are suppressed while complete down/up tick pairs remain distinct. Session pause, disconnect, cancellation, and permission loss release decoder-owned held keys. Disconnect can reconnect only after a fresh unique-target check; permission loss fails the session without prompting or retrying.

The live connection opens with the non-seizing option before installing input/removal callbacks or the cancel handler. Those callbacks carry an unretained connection context, so a failed open leaves no registered callback context behind; registration completes before activation.

This task's replay tests and builds are synthetic/source-only evidence. No HID device was enumerated or opened for this implementation, and no live capture, permission, disconnect, or sleep/resume behavior has been verified. The exact keyboard interface descriptor shape exposed by macOS therefore remains an explicit physical-check prerequisite; the adapter currently accepts only an unambiguous set of individual usage elements and refuses array layouts. The current app entry point is still a placeholder, so the producer is available for `ActionRuntime` injection but is not started by the app.

`ReportID3KeyboardEncoder` constructs source-derived Report ID 3 keyboard sequences of 1–5 USB HID keyboard usages. Those bytes are not macOS virtual key codes. Its broader vectors have not been physically verified. The callable USB transport accepts the exact nine original letter vectors, the separately validated layer-1 slot-1 `z` vector, the nine fixed F16–F24 vectors, and fixed LED mode-1 and mode-2 sequences. Each future persistent write still needs specific user consent. The [manufacturer guide](https://sikaicase.com/blogs/news/before-software-setting) describes LED mode 2 as a color gradient. After the fixed mode-2 transfer was accepted, the User observed the keypad cycling green, purple, blue, yellow, red, and teal. Each color lights one key at a time: bottom-left, middle-left, top-left, bottom-right, middle-right, top-right. Pressing keys did not alter the sequence. The User observed the same sequence after one unplug/reconnect.

`ObservedDeviceProgrammingCapabilities.observedUnit` is a read-only catalog for downstream code. It now records the nine current upright-control/layer-1/slot/F16–F24 usage vectors in the table and lighting modes 1 and 2. It is evidence about this tested unit after the recorded reconnect, not live device settings, a live detection result, or permission to issue a write. Other layers, unobserved usages, macros, consumer controls, and mouse/wheel actions are not in the observed catalog.

After the separately approved mode-1 transfer, the User observed slow blinking colors during press and release events on the left-column keys. Reported press/release pairs cycled teal/green, purple/blue, and yellow/red. Bottom-left blinked red at idle before the first press; middle-left and top-left were unlit at idle. After one unplug/reconnect, all LEDs were initially off; following two quick bottom-right presses, purple became steady at idle. A later held bottom-right press changed purple to blue, and release changed it to yellow. This establishes User-observed press/release lighting after one reconnect, without establishing exact timing, which other keys light, or a universal color order. The transport labels each transfer `sentUnverified`; software cannot itself verify the visible effect. Media, mouse, LED mode 0, arbitrary keyboard usages outside the exact transport allowlist, other layers, and macros remain unavailable. There is no configuration readback or verified restoration method.

Static inspection of the user-supplied Windows app shows that its LED download flow sends a layer-select report before the mode report and the LED-specific save report. Each bounded lighting vector sends exactly three 65-byte Report ID 3 reports on layer 1: `[03 a1 01]`, `[03 b0 18 01]` for mode 1 or `[03 b0 18 02]` for mode 2, and `[03 aa a1]`, with every remaining byte zero. The corresponding physical observations are above.

`KeyboardDeviceProgrammingService` requires an explicit slot and `acceptsPersistentOverwrite` request field for keyboard assignments. Lighting requests also require that explicit flag and can emit only a fixed layer-select/mode/save sequence for mode 1 or 2. Earlier user approvals covered only the completed experiments; they do **not** authorize later invocations. Any app integration must obtain a fresh, specific user decision before invoking another persistent write. An accepted report sequence returns `sentUnverified`; it never asserts behavior or retention. A rejected/short report stops the sequence before later reports or flash save. A failed or interrupted save leaves persistence unknown. The async caller waits for the synchronous C operation and teardown before receiving a result, even after cancellation. Waiting for the process-wide operation lock and each next report is cancellation-aware. A cancellation signal between the pre-write check and `interrupt_transfer` may still allow that transfer to begin; a completed save is reported as sent if cancellation arrives during that last transfer.

## F16–F24 remap execution — 2026-10-06

The User approved a staged remap of layer-1 slots 1–6 and 13–15 to F16–F24. Stage 1 wrote slot 1 → F16 (`0x6B`), with four reports accepted by the host. After one reconnect, a target-only capture confirmed bottom-left emitted page-7 usage `0x6B` down/up; the User affirmed that check. Stage 2 then wrote slots 2, 3, 4, 5, 6, 13, 14, and 15 in order to F17–F24. Each write reported four host-accepted reports, for 32 total. No retry or restoration was attempted.

After Stage 2, the User reconnected once more. The full target-only capture recorded the nine expected F usages and down/up pairs in the gesture order listed above. F16–F24 are function-key events, not printable letters; they may invoke OS or application bindings. The user checked that Keyboard Maestro, Karabiner, and BetterTouchTool were not installed or running in the searched local locations, but this does not rule out other system or application behavior. The observer was nonexclusive and did not collect application-side effects. See `.apm/evidence/hardware/fkey-remap-2026-10-06/stage1-write.md`, `stage2-write.md`, and `stage2-capture.md` for runner identity, host transfer results, reconnect checks, and capture details.

Each remap used one layer-1, zero-modifier keyboard stroke and four zero-padded 65-byte Report ID 3 reports: `[03 A1 01]`; `[03 SS 11 01 00 00 00]`; `[03 SS 11 01 01 00 UU]`; `[03 AA AA]`. The report bytes are followed by zeroes to 65 bytes. Here `SS` is the slot and `UU` is the usage. The host-accepted writes plus the post-reconnect input capture establish observed behavior for this unit; the keypad has no settings readback, and the recorded letter restore target is not guaranteed or verified. Future persistent writes require a fresh, specific user decision.

The nine F16–F24 vectors are now in the observed capability catalog for this unit. Source-derived macros, consumer controls, mouse/wheel actions, and layers 2–3 remain gated and unverified. The transport's broader exact allowlist is not permission for an app to write without user consent.

The C transport holds one process-wide lock from discovery through release, so separate service instances cannot interleave report sequences. It rejects a report-buffer length mismatch before reading the buffer, re-enumerates for exactly one matching VID/PID unit, validates its four-interface topology, opens that same device, claims interface 1, and checks the full Report ID 3 descriptor again on the open handle before output. All reports go only to endpoint `0x02`. It never switches to an unobserved fallback route. Same-ID, same-topology replacement hardware without serial identity remains indistinguishable.

The C bridge loads `libusb-1.0.dylib` at runtime from `/opt/homebrew/lib` or `/usr/local/lib`. If neither exists, programming returns unavailable. The app does not bundle libusb; standalone distribution remains incomplete until the dependency and its license/packaging are addressed. Separately approved lighting writes are recorded in `.apm/evidence/hardware/led-mode2-write-2026-10-06.md` and `.apm/evidence/hardware/led-mode1-write-2026-10-06.md`.
